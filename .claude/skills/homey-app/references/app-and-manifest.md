## App folder layout {#app-folder-layout}

```
com.athom.example/
├─ .homeycompose/
│  ├─ app.json
│  └─ ...                # see "Homey Compose" below
├─ .homeybuild/          # CLI build output — gitignored
├─ .python_cache/        # Python runtime only: pre-compiled venvs
├─ assets/
│  ├─ icon.svg
│  └─ images/
│     ├─ small.png       # 250 x 175
│     ├─ large.png       # 500 x 350
│     └─ xlarge.png      # 1000 x 700 (optional)
├─ drivers/
│  └─ my_driver/
│     ├─ assets/
│     │  ├─ icon.svg
│     │  └─ images/{small,large,xlarge}.png   # 75x75 / 500x500 / 1000x1000
│     ├─ device.js
│     └─ driver.js
├─ locales/
│  ├─ en.json
│  └─ nl.json
├─ settings/
│  └─ index.html         # optional App Settings page (not allowed on Homey Cloud)
├─ api.js                # optional App Web API (not available on Homey Cloud)
├─ app.js
├─ app.json              # GENERATED by Homey Compose — never hand-edit
├─ env.json              # secrets — add to .gitignore
└─ README.txt            # App Store long description (plain text)
```

Runtime-specific entry points:

| Runtime | App | Driver / Device | Web API | Extra |
| --- | --- | --- | --- | --- |
| JavaScript (CommonJS) | `app.js` | `driver.js`, `device.js` | `api.js` | — |
| JavaScript (ESM) | `app.mjs` / `app.cjs` | `driver.mjs`, `device.mjs` (or `.cjs`) | `api.mjs` / `api.cjs` | Triggered by `"type": "module"` in `package.json`; Compose then writes `"esm": true`. Requires `"compatibility": ">=12.0.1"` |
| TypeScript | `app.mts` | `driver.mts`, `device.mts` | `api.mts` | `tsc` `outDir` must be `./.homeybuild` |
| Python | `app.py` | `driver.py`, `device.py` | `api.py` | `.python_cache/` (pre-compiled deps) |

Additional root files:

| File | Purpose |
| --- | --- |
| `/.homeyignore` | Works like `.gitignore`; excludes files/folders from the published bundle. By default **all** files in the app directory are included. |
| `/README.<lang>.txt` | Translated App Store long description, e.g. `README.nl.txt`. |
| `/.homeychangelog.json` | Per-version changelog (see [Internationalization](#internationalization)). `homey app create` seeds it with `{ "<version>": { "en": "First version!" } }`. |
| `/.gitignore` | `homey app create` scaffolds it with `/env.json`, `/node_modules/`, `/.homeybuild/`. Note it does **not** ignore `/app.json` — see the ENOENT gotcha below. |

`/.homeyignore` example:

```
comments.txt
docs/*
```

## App class (`/app.js`) {#app-class}

`Homey.App` is the entry point of every app. It is **instantiated once** when the app starts, is
extended and exported from `app.js`, and **the constructor may not be overridden** — put startup
logic in `onInit()`. Methods prefixed with `on` are meant to be overridden. `App` extends
`SimpleClass`, which provides `log()` and `error()`.

```javascript
'use strict';

const Homey = require('homey');
const ApiClient = require('your-external-api-client');

class MyApp extends Homey.App {

  async onInit() {
    this.log('MyApp has been initialized');

    // Shared state: create expensive singletons once, here.
    this.client = new ApiClient({
      clientId: Homey.env.CLIENT_ID,
      token: this.homey.settings.get('token'),
    });

    // App-level Flow cards are registered once, here.
    this.homey.flow.getActionCard('do_something')
      .registerRunListener(async (args, state) => {
        await this.client.doSomething(args.value);
      });

    // Timers MUST go through this.homey so they are disposed with the app.
    this.pollInterval = this.homey.setInterval(() => {
      this.poll().catch(this.error);
    }, 30_000);
  }

  async poll() {
    const data = await this.client.getData();
    this.log('polled', data);
  }

  async onUninit() {
    // Called when the app is destroyed. Release everything you created in onInit().
    this.homey.clearInterval(this.pollInterval);
    this.client.destroy();
  }

}

module.exports = MyApp;
```

### App instance properties & methods

| Member | Type | Description |
| --- | --- | --- |
| `this.homey` | `Homey` | The `Homey` instance of this app — the gateway to every manager. |
| `this.id` | `string` | The app id. |
| `this.manifest` | `any` | The parsed `app.json` manifest. |
| `this.sdk` | `number` | The app SDK version. |
| `async onInit()` | — | Called upon initialization of the app. |
| `async onUninit()` | — | Called when the app is destroyed. |
| `this.log(...args)` | — | Emits the `__log` event with `args`. |
| `this.error(...args)` | — | Emits the `__error` event with `args`. |

### Reaching the App instance from a Driver or Device

```javascript
'use strict';

const Homey = require('homey');

class MyDevice extends Homey.Device {

  async onInit() {
    // this.homey.app is a pointer to the App instance
    const data = await this.homey.app.client.getData();
    this.setCapabilityValue('measure_temperature', data.temperature).catch(this.error);
  }

}

module.exports = MyDevice;
```

### Lifecycle rules (multi-tenancy safe)

On Homey Cloud several app instances live inside **one** Node.js process (multi-tenancy), and an app
may run on several servers. These rules are mandatory there and good practice everywhere:

- **Never mutate module-level (global) variables** — the global scope is shared between instances.
  Store per-instance state as properties on the `App`, `Driver` or `Device` instance.
  ```javascript
  // BAD: shared between app instances
  let count = 0;
  class App extends Homey.App { onInit() { count += 1; } }

  // GOOD
  class App extends Homey.App { onInit() { this.count = (this.count ?? 0) + 1; } }
  ```
- **Clean up in `onUninit()`** — `App#onUninit()`, `Driver#onUninit()` and `Device#onUninit()` are
  called when the instance is destroyed. On Homey Pro the whole process dies; on Homey Cloud it does
  not.
- **Use `this.homey.setTimeout` / `this.homey.setInterval` / `this.homey.clearTimeout` /
  `this.homey.clearInterval`** instead of the globals — they are automatically disposed when the
  Homey instance is destroyed.
- **Never leave a promise rejection unhandled** — on Homey Cloud an unhandled rejection crashes the
  app. For fire-and-forget calls append `.catch(this.error)`, e.g.
  `this.setCapabilityValue('onoff', false).catch(this.error);`.
- **Use relative paths only** — on Homey Pro apps are sandboxed/chroot'ed so `/` is the app
  directory; on Homey Cloud apps run in Docker where `/` is the Linux root. Always
  `require('./assets/foo.js')` or `path.join(__dirname, 'myfile.svg')`.

See `references/homey-cloud.md` for the full Homey Cloud restriction list.

### System events

```javascript
this.homey.on('memwarn', ({ count, limit }) => this.log(`memwarn ${count}/${limit}`));
this.homey.on('cpuwarn', ({ count, limit }) => this.log(`cpuwarn ${count}/${limit}`));
this.homey.on('unload', () => this.log('app is being stopped'));
```

| Event | Payload | Fired when |
| --- | --- | --- |
| `memwarn` | `{ count, limit }` | The app uses too much memory. If it does not behave within a reasonable time it is killed. `count` = warnings sent so far, `limit` = max warnings before the kill. |
| `cpuwarn` | `{ count, limit }` | The app uses too much CPU. Same kill semantics. |
| `unload` | — | The app is being stopped. |

## Platform & feature detection {#platform-detection}

Read `this.homey.platform` and `this.homey.platformVersion` to know which product the app runs on.

| Product | `platform` | `platformVersion` |
| --- | --- | --- |
| Homey Cloud | `cloud` | `1` |
| Homey (Early 2016) | `local` | `1` |
| Homey (Early 2018) | `local` | `1` |
| Homey (Early 2019) | `local` | `1` |
| Homey Pro (Early 2019) | `local` | `1` |
| Homey Pro (Early 2023) | `local` | `2` |
| Homey Pro mini (2025) | `local` | `2` |
| Homey Pro (2026) | `local` | `2` |
| Homey Self-Hosted Server | `local` | `2` |

> On older software versions either property may be `undefined` — in that case assume
> `platform === 'local'` and `platformVersion === 1`.

### `platformFeatures` / `hasFeature()`

`this.homey.platformFeatures` is a `string[]`; `this.homey.hasFeature(feature)` returns a boolean
(**Homey v12.7.1+**). Documented feature strings:

| Feature | Meaning |
| --- | --- |
| `speaker` | Homey has a speaker (e.g. for speech output). |
| `ledring` | Homey has the LED ring. |
| `nfc` | Homey has an NFC reader. |
| `camera-streaming` | Homey supports camera streaming. |
| `matter` | Homey supports Matter. |
| `ble-advertisements` | Homey supports BLE advertisement subscriptions (`ManagerBLE#subscribeToAdvertisements`). Supported on Homey Pro (Early 2023), Homey Pro Mini, Homey Pro 2026 and Homey SHS. |

```javascript
'use strict';

const Homey = require('homey');

class MyApp extends Homey.App {

  async onInit() {
    if (this.homey.platform === 'cloud') {
      this.log('running on Homey Cloud — no LAN access');
    }

    if (this.homey.hasFeature('ledring')) {
      // safe to use this.homey.ledring
    }

    if (this.homey.hasFeature('ble-advertisements')) {
      // subscribe; otherwise fall back to polling with ManagerBLE#find()
    }
  }

}

module.exports = MyApp;
```

> **Gotcha:** `hasFeature()` only exists on Homey v12.7.1 and later. If your `compatibility` range
> allows older firmware, guard with `typeof this.homey.hasFeature === 'function'` or fall back to
> inspecting `this.homey.platformFeatures`.

Feature *detection* (`hasFeature`) is a superset of the manifest's
[`platformLocalRequiredFeatures`](#app-manifest), whose documented values are `nfc`, `ledring`,
`speaker` and `matter` (the JSON schema additionally accepts `camera-streaming`; `ble-advertisements`
is **not** accepted there — detect it at runtime).

Rule of thumb: use `platformLocalRequiredFeatures` when the app is unusable without the feature (it
makes the app uninstallable), and `hasFeature()` when you can degrade gracefully.

## App Manifest {#app-manifest}

All basic information lives in `/.homeycompose/app.json`; Homey Compose merges it (plus every
`*.compose.json` and the other `.homeycompose/` files) into the generated `/app.json`.

```json
{
  "id": "my.company.example",
  "version": "1.0.0",
  "compatibility": ">=5.0.0",
  "runtime": "nodejs",
  "platforms": ["local", "cloud"],
  "sdk": 3,
  "brandColor": "#FF0000",
  "name": { "en": "My App" },
  "description": { "en": "Adds support for Example devices." },
  "category": "lights",
  "tags": { "en": ["example"] },
  "images": {
    "small": "/assets/images/small.png",
    "large": "/assets/images/large.png",
    "xlarge": "/assets/images/xlarge.png"
  },
  "permissions": ["homey:manager:api"],
  "author": {
    "email": "john@doe.com",
    "name": "John Doe"
  }
}
```

### Core properties

| Property | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `string` | yes | The app id, in reversed domain-name notation (`com.company.product`). |
| `version` | `string` | yes | [Semantic Version](http://semver.org). Pre-release versions (`1.0.0-rc.1`) are **not allowed**. |
| `compatibility` | `string` | yes | Semver range of compatible Homey versions. Use at least `">=5.0.0"`. |
| `runtime` | `"nodejs"` \| `"python"` | see notes | The runtime the app is written for; allowed values are `nodejs` and `python`. Every manifest example in the docs declares it; the Python-only properties below are required only when it is `"python"`. |
| `platforms` | `("local" \| "cloud")[]` | no | Supported platforms. `local` = Homey Pro / Self-Hosted Server, `cloud` = Homey Cloud. |
| `sdk` | `number` | yes | SDK level — must be `3`. |
| `brandColor` | `string` (HEX) | yes for the store | Brand color, used as backdrop for icons in Flows, Add devices and the App Store. **Not allowed to be very bright**; both app and driver icons must stay clearly visible against it. |
| `name` | translation object | yes | Name of the app. |
| `description` | translation object | yes | Description — a **one-liner**. |
| `category` | `string` | yes | App Store category (see list below). |
| `tags` | translation object of arrays | no | Searchable App Store tags, e.g. `{ "en": ["example"] }`. |
| `images` | `{ small, large, xlarge? }` | yes | Paths to the App Store images. `small` and `large` are mandatory, `xlarge` optional. |
| `permissions` | `string[]` | no | See [Permissions](#permissions). |
| `author` | `{ name, email? }` | yes | `author.name` is required, `author.email` optional. |

**Allowed `category` values (exactly one string):**
`lights`, `video`, `music`, `appliances`, `security`, `climate`, `tools`, `internet`,
`localization`, `energy`.

**Image resolutions** (guideline 1.4.1, `.jpg` or `.png`):

| | small | large | xlarge (optional) |
| --- | --- | --- | --- |
| App images | 250 × 175 | 500 × 350 | 1000 × 700 |
| Driver images | 75 × 75 | 500 × 500 | 1000 × 1000 |

The validator checks the file's magic bytes (`.png`, `.jpg`, `.jpeg` only), its case-sensitive
existence and the **exact** pixel size of `small` and `large`.

### Validation levels

`homey app validate --level <debug|publish|verified>` (default `debug`). Each level adds
requirements:

| Level | Additionally requires |
| --- | --- |
| `debug` | Schema validity + all rules below that are level-independent |
| `publish` | `category`, `brandColor`, `images` (present and correctly sized), no symlinked (`npm link`) modules in `node_modules`, `energy.batteries` for drivers using `measure_battery`/`alarm_battery`, cross-platform venvs for Python apps with dependencies |
| `verified` | `platforms` and `support` on the app; `platforms` and `connectivity` on every driver; `homey:manager:speech-input` becomes a hard error |

Level-independent field rules enforced by the validator:

| Field | Rule |
| --- | --- |
| `id` | At least one `.`, and matches `^[a-zA-Z0-9_.-]*$` |
| `version` | `semver.coerce(version) === version` — so `1.0.0-rc.1` and `1.0.0+build` fail |
| `compatibility` | Valid semver **range**; `sdk: 3` needs a minimum `> 4.2.0`, i.e. `>=5.0.0` |
| `brandColor` | Exactly 7 chars (`#RRGGBB`) and brightness ≤ 184 — "Icons are rendered white, so choose a darker color that has enough contrast" |
| `category` | Every entry must be one of the ten categories |
| `permissions` | Every entry must be a known permission id or `homey:app:*` |
| `platformLocalRequiredFeatures` | Cannot be combined with `"cloud"` in `platforms` (hard error); warns when `platforms` lacks `"local"` |
| `/locales/<x>.json` | `<x>` must be a valid ISO-639-1 code and the file must be valid JSON |
| `/env.json` | Keys uppercase, values strings |
| `/assets/icon.svg` | Must exist |
| `/settings/` | If the folder exists, `/settings/index.html` must exist |

### Python runtime properties

Only required when `"runtime": "python"`.

| Property | Type | Description |
| --- | --- | --- |
| `pythonVersion` | `string` | Python version the app was developed for. Currently the only documented supported version is `"3.14"` (the validator also still accepts `"3.13"`). |
| `pythonDependencies` | `string[]` | Dependencies, e.g. `["aiohttp>=3.13"]`. Managed **only** through `homey app dependencies install` / add / remove. |

```jsonc
{
  "id": "com.athom.example",
  // ...
  "compatibility": ">=13.0.0",
  "runtime": "python",
  "pythonVersion": "3.14",
  "pythonDependencies": ["aiohttp>=3.13"]
}
```

> **Gotcha — the dependency array has two names.** The documentation calls it `pythonDependencies`,
> but homey CLI v4.4.0 and the `homey-lib` v2.51.4 app schema read and write it as
> **`pythonPackages`** (that is the key the CLI writes into the manifest, and the key the publish
> check for cross-platform venvs inspects). Since you should never hand-edit it either way, always
> let `homey app dependencies add|remove|install` manage the manifest, and do not be surprised when
> the generated `app.json` disagrees with the docs.

> **Warning:** editing the dependency array by hand without running `homey app dependencies install`
> bundles the app with outdated libraries; installing dependencies through any other means (plain
> `pip`, `uv`) leaves them out of the bundle entirely. Always test with `homey app install` / remote
> run after changing dependencies. Publishing a Python app that declares dependencies additionally
> requires pre-compiled venvs for **both** `arm64` and `amd64`. If the declared `pythonVersion`
> becomes outdated a newer interpreter may be used, which can break the app; apps get roughly a year
> to move to a new full-release Python version.

### Additional (optional) properties

| Property | Type | Description |
| --- | --- | --- |
| `platformLocalRequiredFeatures` | `("nfc" \| "ledring" \| "speaker" \| "matter")[]` | Required features for platform `local`. Makes the app **uninstallable** on Homey Pros lacking any listed feature — only use it when the app cannot function without them. The JSON schema also accepts `camera-streaming`. |
| `platformLocalOptionalFeatures` | same enum | Accepted by the schema and validator but not documented on the docs site; warns when `platforms` lacks `"local"`. Prefer runtime `hasFeature()`. |
| `contributors` | `{ developers: [{ name, email?, website? }], translators: [...] }` | Credits. Each entry must contain `name`; only the keys `developers` and `translators` are allowed. This — not the README — is where contributors belong. |
| `contributing.donate` | `{ paypal?, bunq?, patreon?, githubSponsors? }`, each `{ username }` | Adds a *Donate* button on the app page. Only visible for **non-verified** developers. `paypal` additionally accepts `email`, `fundraiserCharityId` (number) and `currency`. |
| `bugs` | `{ url }` | Public bug/issue tracker URL; must match `^https?://`. |
| `homeyCommunityTopicId` | `number` | Topic id from the [Homey Community](https://community.athom.com/) forum URL; shows a link on the App Store. |
| `athomForumDiscussionId` | `number` | Legacy predecessor of `homeyCommunityTopicId`, still accepted by the schema. |
| `source` | `string` | Source-code URL, must start with `https://`. |
| `homepage` | `string` | Company/brand/personal page, must start with `https://`. |
| `support` | `string` | Support URL or e-mail; starts with `https://` or `mailto:`. **Mandatory for Verified Developers.** |
| `api` | `object` | App Web API routes (`{ handlerName: { method, path, public? } }`). Not available on Homey Cloud — see `references/web-api-and-realtime.md`. |
| `settings` | `array` | Legacy typed app-settings form (`text`, `password`, `textarea`, `label`, `number`, `slider`, `radio`, `dropdown`, `checkbox`, `group`), still in the JSON schema. The documented way to build an app settings page is `/settings/index.html`. |

### Manifest keys produced by Compose

These do not live in `/.homeycompose/app.json`; Compose generates them into `/app.json` from other
files: `drivers` (from `drivers/*/driver.compose.json`), `flow`, `capabilities`, `discovery`,
`signals`, `screensavers`, `widgets`. Schemas are documented in `references/drivers-and-devices.md`,
`references/capabilities.md`, `references/flow-cards.md`, `references/widgets.md`,
`references/wireless-lan-discovery.md` and `references/wireless-rf-infrared.md`.

The CLI injects a few more keys into the generated `/app.json` at run/build time — never write them
by hand:

| Key | Set when |
| --- | --- |
| `_comment` | Always: `"This file is generated. Please edit .homeycompose/app.json instead."` |
| `esm: true` | `package.json` contains `"type": "module"` |
| `hasSettings: true` | `/settings/index.html` exists |
| `iconHash`, `drivers[].iconHash`, `capabilities[].iconHash` | Hash of `assets/icon.svg` / driver icons / capability icons |

### Compatibility gates

Validation fails when a manifest uses a feature newer than its declared `compatibility` range:

| Feature | Minimum `compatibility` |
| --- | --- |
| `sdk: 3` | `>=5.0.0` |
| ESM (`app.mjs`/`app.cjs`/`api.mjs`/`api.cjs`, driver/device/widget `.mjs`/`.cjs`, `esm: true`) | `>=12.0.1` |
| `widgets`, `widgets[].transparent` | `>=12.1.0` |
| `widgets[].deprecated`, `widgets[].devices` | `>=12.3.0` |
| `runtime: "python"` (also requires `sdk: 3`) | `>=13.0.0` |
| `capabilities[].titleShort` | `>=13.2.1` |

### Naming, id and platform gotchas

> **Gotcha — the app `id` is effectively permanent.** After the first publish, changing it creates a
> brand-new App Store listing that loses all existing installs and reviews. Settle on the final id
> *before* you publish. Reverse-domain notation. You may not use the Homey or Athom name as the
> **identity** of the id (do not impersonate them, no `com.athom.*`), but this is not a literal
> substring ban — `com.you.homeyfin` for a Jellyfin app is fine.

> **Gotcha — `name` and `description` are store-reviewed.** `name` should be at most **4 words**, be
> the brand name, and contain no company names, no protocol names (Zigbee, Z-Wave, 433 MHz…) and no
> "Homey"/"Athom". `description` is a single catchy one-liner, not a paragraph; do not repeat the app
> name, do not reuse README text, and avoid "Adds support for X" / "Integrates X with Homey". Full
> rules in `references/publishing.md`.

> **Gotcha — default to `"platforms": ["local"]`.** Publishing an app that targets
> `["cloud"]` or `["local", "cloud"]` requires the **Homey Verified Developer** subscription, and only
> official integrations (submitted by the brand, or by a developer commissioned by the brand) are
> approved. Without it `homey app publish` is rejected with *"Your account is not eligible to publish
> apps for Homey Cloud."* Publishing for Homey Pro is free and requires no subscription. Note that
> `platforms` (where the *app* can run) is independent of a driver's `connectivity` (how the *device*
> talks) — a local-only app can still integrate a cloud API.

> **Gotcha — pre-release versions are rejected.** `1.0.0-rc.1` fails validation. Bump with
> `homey app version <patch|minor|major>`.

Homey Cloud also requires the `platforms` array on Flow cards and drivers:
`"platforms": ["local", "cloud"]` in `/.homeycompose/flow/<type>/<id>.json` and in
`driver.compose.json` (which additionally takes `connectivity`).

## Homey Compose {#homey-compose}

Homey Compose splits the manifest across many small files and merges them into `/app.json` at
build/run/publish time.

### Complete file layout

```
com.athom.example/
├─ .homeycompose/
│  ├─ app.json                      # core manifest properties
│  ├─ capabilities/
│  │  └─ <id>.json                  # custom capabilities
│  ├─ screensavers/
│  │  └─ <id>.json                  # LED ring screensavers: { "title": { "en": "…" } }
│  ├─ signals/
│  │  ├─ 433/
│  │  │  └─ <id>.json               # 433 MHz signal definitions
│  │  ├─ 868/
│  │  │  └─ <id>.json               # 868 MHz signal definitions
│  │  └─ ir/
│  │     └─ <id>.json               # infrared signal definitions
│  ├─ flow/
│  │  ├─ triggers/
│  │  │  └─ <id>.json               # app-level Flow triggers
│  │  ├─ conditions/
│  │  │  └─ <id>.json
│  │  └─ actions/
│  │     └─ <id>.json
│  ├─ discovery/
│  │  └─ <id>.json                  # mDNS-SD / SSDP / MAC discovery strategies
│  ├─ drivers/
│  │  ├─ templates/
│  │  │  └─ <template_id>.json      # shared driver properties, pulled in with $extends
│  │  ├─ settings/
│  │  │  └─ <setting_id>.json       # shared device-setting definitions ($extends)
│  │  └─ flow/
│  │     ├─ triggers/
│  │     │  └─ <id>.json            # driver Flow cards shared by several drivers
│  │     ├─ conditions/
│  │     │  └─ <id>.json
│  │     └─ actions/
│  │        └─ <id>.json
│  └─ locales/
│     ├─ <locale>.json
│     └─ <locale.foo>.json
└─ drivers/
   └─ <driver_id>/
      ├─ driver.compose.json        # driver manifest
      ├─ driver.flow.compose.json   # Flow cards scoped to this driver
      └─ driver.settings.compose.json  # device settings (array)
```

| File / folder | Produces | Schema documented in |
| --- | --- | --- |
| `.homeycompose/app.json` | top-level manifest fields | this file |
| `.homeycompose/capabilities/<id>.json` | `capabilities` | `references/capabilities.md` |
| `.homeycompose/screensavers/<id>.json` | `screensavers` — registered at runtime with `animation.registerScreensaver('<id>')` | `references/advanced-features.md` |
| `.homeycompose/signals/{433,868,ir}/<id>.json` | `signals.<frequency>` — used via `this.homey.rf.getSignal433/868/Infrared('<id>')` | `references/wireless-rf-infrared.md` |
| `.homeycompose/flow/{triggers,conditions,actions}/<id>.json` | app-level Flow cards | `references/flow-cards.md` |
| `.homeycompose/discovery/<id>.json` | `discovery` strategies | `references/wireless-lan-discovery.md` |
| `.homeycompose/drivers/templates/<id>.json` | reusable driver fragments (`$extends`) | this file |
| `.homeycompose/drivers/settings/<id>.json` | reusable device-setting fragments (`$extends`) | `references/drivers-and-devices.md` |
| `.homeycompose/drivers/flow/{triggers,conditions,actions}/<id>.json` | driver Flow cards shared across drivers | `references/flow-cards.md` |
| `.homeycompose/locales/<locale>.json` | translations | [Internationalization](#internationalization) |
| `drivers/<id>/driver.compose.json` | one entry in `drivers` | `references/drivers-and-devices.md` |
| `drivers/<id>/driver.flow.compose.json` | driver-scoped Flow cards | `references/flow-cards.md` |
| `drivers/<id>/driver.settings.compose.json` | that driver's `settings` array | `references/drivers-and-devices.md` |

The CLI reads several more Compose files that the docs diagram omits:

| File / folder | Produces |
| --- | --- |
| `drivers/<id>/driver.firmware.compose.json` | `drivers[].firmwareUpdates` (Z-Wave/Zigbee OTA) |
| `drivers/<id>/driver.pair.compose.json` | `drivers[].pair` (array of pair views) |
| `drivers/<id>/driver.repair.compose.json` | `drivers[].repair` |
| `.homeycompose/drivers/pair/<template_id>/index.html` + `assets/` | Copied to `/drivers/<id>/pair/<viewId>.html` (+ `<viewId>.assets/`) for every view that sets `$template` |
| `.homeycompose/drivers/repair/<template_id>/index.html` + `assets/` | Same for repair views |
| `widgets/<id>/widget.compose.json` | `widgets.<id>` (`settings` defaults to `[]`) |

Ids are derived from the file/folder name: driver id = folder name under `/drivers/`, widget id =
folder name under `/widgets/`, everything else = the JSON filename without `.json` (overridable with
`$id` / `$name`). Drivers are processed in sorted order; files and folders starting with `.` are
skipped.

### Templating with `$extends`

Put shared properties in `.homeycompose/drivers/templates/<template_id>.json`, then reference the
template id from `$extends` in `driver.compose.json`. Compose copies all template properties into the
final file; anything you also declare in `driver.compose.json` **overrides** the template value.
`$extends` holds an array of template ids.

```json
// /.homeycompose/drivers/templates/defaults.json
{
  "images": {
    "large": "{{driverAssetsPath}}/images/large.png",
    "small": "{{driverAssetsPath}}/images/small.png"
  },
  "icon": "{{driverAssetsPath}}/icon.svg",
  "capabilities": [],
  "class": "other"
}
```

```json
// /drivers/my_driver/driver.compose.json
{
  "name": {
    "en": "My Driver",
    "nl": "Mijn Driver"
  },
  "$extends": ["defaults"]
}
```

**Merge semantics:**

- `$extends` accepts a single template id or an array. Templates are merged **left to right**, then
  the driver's own properties are applied **last** — the driver always wins.
- The merge is a shallow spread, **except** `capabilitiesOptions`, which is merged key-by-key
  between template and driver so a driver can override one capability's options without losing the
  rest.
- An unknown template id throws (`Invalid driver setting template for driver: <id>`,
  `Invalid driver flow template for driver <id>: <id>`, `Invalid pair template for driver <id>: …`).

The same mechanism exists for device settings (shared definitions in
`.homeycompose/drivers/settings/<setting_id>.json`, pulled into `driver.settings.compose.json` via
`$extends`) and for driver Flow cards (`.homeycompose/drivers/flow/<type>/<id>.json` pulled into
`driver.flow.compose.json`). For an extended setting or flow card, the resulting id is `$id` if
present, otherwise the **last** template id in the `$extends` array.

### Template placeholders

Placeholders are expanded recursively in every string of a **driver** object (at any depth), after
all merging:

| Placeholder | Expands to |
| --- | --- |
| `{{driverId}}` | The driver folder name |
| `{{driverPath}}` | `/drivers/<driver_id>` |
| `{{driverAssetsPath}}` | `/drivers/<driver_id>/assets` |
| `{{driverName}}` | `driver.name.en` |
| `{{driverNameNl}}`, `{{driverNameDe}}`, … | `driver.name.<locale>` falling back to `name.en`. Suffix = locale code with the first letter upper-cased (`nl` → `Nl`) |
| `{{zwaveParameterIndex}}` | The `zwave.index` of the nearest enclosing object (Z-Wave setting templates) |
| `{{assets}}` | Inside a `$template` pair/repair `index.html`: `<viewId>.assets` |

> **Gotcha:** a driver whose `name.en` is missing makes placeholder expansion throw
> `Missing property \`name\` in driver <driver_id>` — even if the offending string is in a template.

### `$`-prefixed directives

Every key starting with `$` is a Compose instruction and is **stripped from the generated
`/app.json`**.

| Directive | Used in | Effect |
| --- | --- | --- |
| `$extends` | `driver.compose.json`, driver settings, driver flow cards | Merge one or more templates |
| `$id` | capability / signal / flow-card / extended-setting files | Override the id derived from the filename or template |
| `$name` | screensaver files | Override the screensaver `name` |
| `$filter` | `driver.flow.compose.json` cards | String or object; appended as query params to the auto-generated `driver_id=<id>` device-argument filter |
| `$deviceName` | `driver.flow.compose.json` cards | Rename the auto-inserted `device` argument (default `device`) |
| `$template` | pair / repair views | Copy a shared HTML view + assets into the driver |
| `$pairOptions` / `$repairOptions` | `driver.compose.json` | `{ "<viewId>": { …options } }`, merged into that view's `options` |
| `$flow` | internal | Holds `driver.flow.compose.json` while composing |

Driver Flow cards automatically receive a first argument
`{ "type": "device", "name": "device", "filter": "driver_id=<driver_id>" }` — never declare it
yourself. See `references/flow-cards.md`.

### Screensavers and signals in Compose

`.homeycompose/screensavers/weather.json` (requires the `homey:manager:ledring` permission):

```json
{
  "title": { "en": "Weather", "nl": "Weer" }
}
```

The screensaver's `name` becomes the filename (`weather`), unless overridden with `$name`. That name
is what the runtime registration uses; the user then picks it under *Settings → LED Ring*:

```javascript
'use strict';

const Homey = require('homey');

class MyApp extends Homey.App {

  async onInit() {
    const myAnimation = await this.homey.ledring.createAnimation({ options: {}, frames: [] });
    await myAnimation.registerScreensaver('weather').catch(this.error);
  }

}

module.exports = MyApp;
```

RF/IR signal definitions live in `.homeycompose/signals/433/<id>.json`,
`.homeycompose/signals/868/<id>.json` and `.homeycompose/signals/ir/<id>.json`, becoming
`signals.433.<id>` etc. and requiring the matching `homey:wireless:*` permission — see
`references/wireless-rf-infrared.md`.

### Compose locale files

`.homeycompose/locales/<lang>.json` is **deep-merged into** `/locales/<lang>.json`, which Compose
then rewrites. Extra dot-segments in the filename nest the content: `en.foo.json` lands under `foo`,
`en.foo.bar.json` under `foo.bar`. Files are merged longest-path-first.

Reserved top-level keys inside a Compose locale file push their translation into the **manifest**
instead of the locale file — this is how you keep all of one language's strings in a single file:

| Key path | Fills in `app.json` |
| --- | --- |
| `$app.name`, `$app.description` | `name.<lang>`, `description.<lang>` |
| `$capabilities.<id>.{title,titleShort,units}` | `capabilities.<id>.*.<lang>` |
| `$drivers.<id>.name` | `drivers[].name.<lang>` |
| `$drivers.<id>.capabilitiesOptions.<cap>.{title,titleShort,units}` | driver `capabilitiesOptions` |
| `$drivers.<id>.{pair,repair}.<viewId>.options.<key>` | pair/repair view `options` |
| `$drivers.<id>.settings.<settingId>.{label,hint,units}`, `.values.<valueId>.label` | driver settings (groups are flattened, so use the child setting's id) |
| `$drivers.<id>.zwave.learnmode.instruction`, `.zwave.associationGroupsOptions.<n>.hint`, `.zwave.multiChannelNodes.<n>.name` | Z-Wave driver strings |
| `$drivers.<id>.zigbee.learnmode.instruction` | Zigbee driver strings |
| `$drivers.<id>.matter.learnmode.instruction` | Matter driver strings |
| `$flow.<type>.<cardId>.{title,titleFormatted,hint}` | Flow card strings |
| `$flow.<type>.<cardId>.args.<argName>.{title,label,placeholder}`, `.values.<valueId>.title` | Flow card arguments |
| `$flow.<type>.<cardId>.tokens.<tokenName>.{title,example}` | Flow card tokens |
| `$widgets.<id>.name`, `.settings.<settingId>.{title,placeholder}`, `.settings.<settingId>.values.<valueId>.title` | Widget strings |

```json
// /.homeycompose/locales/nl.json
{
  "$app": { "name": "Mijn App", "description": "Voegt ondersteuning toe voor Example-apparaten." },
  "$drivers": { "my_driver": { "name": "Mijn Driver" } },
  "$flow": { "actions": { "do_something": { "title": "Doe iets" } } },
  "pair": { "press_button": "Druk op de `pair` knop." }
}
```

> **Gotcha:** Compose **overwrites** `/locales/<lang>.json` for every language it touched (the merge
> is additive, so hand-written keys survive, but the file is reformatted and the `$…` namespaces are
> consumed). Once you use `.homeycompose/locales/`, author strings there — not in `/locales/`.

### `/app.json` generation

- `/app.json` is **generated** — never hand-edit it. Edit `.homeycompose/*.json` and
  `*.compose.json` instead.
- `homey app run`, `homey app install`, `homey app build`, `homey app validate` and
  `homey app publish` regenerate it (Compose runs whenever a `.homeycompose/` folder exists).
- `homey app version <patch|minor|major|x.y.z>` bumps the version in `.homeycompose/app.json` **and**
  the generated `app.json`.
- `homey app compose` splits a legacy monolithic `app.json` into the `.homeycompose/` layout
  (existing files are preserved, and it refuses to run with uncommitted git changes) — only useful
  for apps that predate Homey Compose.
- If `.homeycompose/` exists but `.homeycompose/app.json` does not, the CLI warns
  ("Could not find a Homey Compose app.json manifest!") and keeps using the root `app.json` as the
  manifest source.

> **Gotcha — `ENOENT: no such file or directory, open 'app.json'` on a fresh Compose-only repo.**
> Compose reads the root `/app.json` **first** and only then overlays `.homeycompose/app.json`, so a
> missing `/app.json` breaks `homey app build`, `run`, `validate` and `publish` alike — building does
> **not** bootstrap it. Fix it by committing the generated `app.json` (which is what
> `homey app create` produces) or by dropping a placeholder `app.json` containing `{}` in the app
> root before the first Compose run; the next run replaces it with the real generated manifest.

## Internationalization {#internationalization}

There are **four separate localization mechanisms**, each with its own file convention.

### 1. In-app strings — `/locales/<language>.json`

```json
// /locales/en.json
{
  "title": "Hello World",
  "greeting": "Hello, __name__",
  "settings": {
    "title": "My Title",
    "intro": "This is an example page."
  },
  "pair": {
    "press_button": "Press the `pair` button on your device."
  }
}
```

```json
// /locales/nl.json
{
  "title": "Hallo Wereld",
  "greeting": "Hallo, __name__",
  "settings": {
    "title": "Mijn Titel",
    "intro": "Dit is een voorbeeld pagina."
  },
  "pair": {
    "press_button": "Druk op de `pair` knop op jou apparaat."
  }
}
```

- IDs use **dot notation** for nested keys: `title`, `greeting`, `settings.title`, `settings.intro`,
  `pair.press_button`.
- Variables are wrapped in **double underscores**: `"Hello, __name__"`.
- If a key is missing in the user's locale, Homey falls back to **English**, so `en` is always
  required.

```javascript
'use strict';

const Homey = require('homey');

class MyApp extends Homey.App {

  async onInit() {
    this.log(this.homey.__('title'));                        // "Hello World"
    this.log(this.homey.__('greeting', { name: 'Dave' }));   // "Hello, Dave"
    this.log(this.homey.__({ en: 'My String', nl: 'Mijn tekst' })); // inline object
  }

}

module.exports = MyApp;
```

`ManagerI18n` (`this.homey.i18n`):

| Method | Returns | Description |
| --- | --- | --- |
| `__(key, tags)` | `string \| null` | Translate a string from `/locales/<language>.json`. Returns `null` when the key is not found. Also exposed as `this.homey.__()`. |
| `getLanguage()` | `string` | Homey's current language as a 2-character code (e.g. `en`). |
| `getUnits()` | `string` | `metric` or `imperial`. |

### 2. Translation objects inside the manifest

Instead of a locale key, manifest/compose files take an object keyed by language code:

```json
"title": {
  "en": "Hello, World!",
  "nl": "Hallo, wereld!"
}
```

A plain string is also allowed when translation is unnecessary:

```json
"title": "°C"
```

Manifest/compose fields that are translation objects:

| File | Translation-object fields |
| --- | --- |
| `.homeycompose/app.json` | `name`, `description`, `tags` (object of arrays) |
| `driver.compose.json` | `name`, `capabilitiesOptions[].{title,titleShort,units}`, `zwave/zigbee/matter.learnmode.instruction`, `zwave.associationGroupsOptions[].hint`, `zwave.multiChannelNodes[].name` |
| `.homeycompose/flow/**` and `driver.flow.compose.json` | `title`, `titleFormatted`, `hint`, argument `title`/`label`/`placeholder`, argument `values[].title`, token `title`/`example` |
| `driver.settings.compose.json` | `label`, `hint`, `units`, `values[].label`, and group `label` |
| `driver.pair.compose.json` / `driver.repair.compose.json` | view `options.*` |
| `.homeycompose/capabilities/<id>.json` | `title`, `titleShort`, `units` |
| `.homeycompose/screensavers/<id>.json` | `title` |
| `widgets/<id>/widget.compose.json` | `name`, setting `title`/`placeholder`, setting `values[].title` |
| app `settings` array (legacy) | `title`, `hint`, `units` |

Always include at least `en` — the schema requires it in every translation object.

Instead of writing these objects language-by-language in every file, you can keep one file per
language under `.homeycompose/locales/` and use the `$app` / `$drivers` / `$flow` / `$capabilities` /
`$widgets` namespaces — see [Compose locale files](#homey-compose).

### 3. App Store long description — `README.txt`

`/README.txt` holds the English text; add `/README.<languagecode>.txt` (e.g. `README.nl.txt`,
`README.de.txt`) for translations. Plain text only — no Markdown, no URLs. See
`references/publishing.md`.

### 4. Publish changelog — `/.homeychangelog.json`

Keyed by version, then language. `en` is required per entry; other languages fall back to it. The
CLI appends to this file when you answer the "What's new?" prompt during `homey app publish`.

```json
{
  "1.0.0": { "en": "Initial release.", "de": "Erste Version.", "nl": "Eerste versie." },
  "1.1.0": { "en": "Added widgets." }
}
```

### Custom views (settings, pairing, widgets)

Custom views translate through the same `/locales/*.json` files, either declaratively with
`data-i18n` or programmatically with `Homey.__()`:

```html
<header class="homey-header">
  <h1 class="homey-title" data-i18n="settings.title"></h1>
  <p class="homey-subtitle" data-i18n="settings.intro"></p>
</header>
<script type="application/javascript">
  function onHomeyReady(Homey) {
    alert(Homey.__('settings.title'));
    Homey.ready();
  }
</script>
```

### Supported language codes

| Code | Language | Code | Language |
| --- | --- | --- | --- |
| `en` | English | `da` | Danish |
| `nl` | Dutch | `ru` | Russian |
| `de` | German | `pl` | Polish |
| `fr` | French | `ko` | South Korean |
| `it` | Italian | `ar` | Arabic |
| `sv` | Swedish | | |
| `no` | Norwegian | | |
| `es` | Spanish | | |

English is always required and is the fallback for every other language. Athom is Dutch and Dutch is
a large part of the user base, so **`en` + `nl` (+ `de`)** is a sensible minimum translation set.

> **Gotcha:** the validator only checks that a `/locales/<code>.json` filename is a valid ISO-639-1
> code, not that Homey supports it. `pt.json` therefore passes validation happily and is never shown
> to any user. Stick to the 13 languages above.

### Units and temperature

Apps must always work in **Celsius** internally — Homey converts capability values to Fahrenheit
automatically. For custom capabilities the docs instruct setting the unit to `"°C"` so Homey knows
the value must be converted (the custom-capability schema field is `units`, see
`references/capabilities.md`).

### Right-to-left (Arabic)

Arabic (`ar`) is an RTL language: layout direction, alignment and spacing are mirrored. All built-in
pairing views support RTL out of the box. **Custom** views must handle it yourself with the CSS
`:dir(rtl)` selector:

```css
.my-custom-class { transform: translate(-50%); }
.my-custom-class:dir(rtl) { transform: translateX(50%); }
```

### Auto-translating

```bash
homey app translate --api-key "..."
```

Asks OpenAI to translate all `.json` files and `README.txt`. Requires an OpenAI API key with a
payment method; translating an entire app usually costs less than $1.

## Permissions {#permissions}

Permissions are declared as an array in the App Manifest. Most apps need none. **If a permission is
not requested, the manager methods that require it throw an error.**

```jsonc
// /.homeycompose/app.json
{
  "id": "com.athom.example",
  // ...
  "permissions": [
    "homey:wireless:ble",
    "homey:app:com.athom.example"
  ]
}
```

| Permission | Unlocks |
| --- | --- |
| `homey:manager:api` | `ManagerApi` (`this.homey.api`) — the Homey Web API, i.e. control over **all** devices and Flows, including those of other apps. |
| `homey:manager:geolocation` | `ManagerGeolocation` (`this.homey.geolocation`) — Homey's current location. |
| `homey:manager:ledring` | `ManagerLedring` (`this.homey.ledring`) — LED ring animations & screensavers. |
| `homey:manager:speech-output` | `ManagerSpeechOutput` (`this.homey.speechOutput`) — make Homey speak. |
| `homey:wireless:433` | `ManagerRF#getSignal433` — the 433 MHz antenna. |
| `homey:wireless:868` | `ManagerRF#getSignal868` — the 868 MHz antenna. |
| `homey:wireless:ir` | `ManagerRF#getSignalInfrared` — sending IR signals. |
| `homey:wireless:ble` | `ManagerBLE` (`this.homey.ble`) — discovering and interacting with Bluetooth LE devices. |
| `homey:wireless:nfc` | `ManagerNFC` (`this.homey.nfc`) — being notified of scanned NFC tags. |
| `homey:app:<appId>` | App-to-app communication with that app's Web API, e.g. `homey:app:com.athom.example`, `homey:app:com.yahoo.weather`. |

Check at runtime with `this.homey.hasPermission('homey:wireless:ble')`.

### Permission ids accepted by the validator but not documented

The validator's permission table also contains `homey:manager:media` ("Control Homey's Music"),
`homey:manager:speech-input` ("React to speech"), `homey:wireless:zwave` and `homey:wireless:zigbee`.
Any other value that does not start with `homey:app:` fails validation with
`Invalid permission: <id>`.

- `homey:manager:speech-input` warns at `debug`/`publish` level ("the homey:manager:speech-input
  permission is not supported, please remove any speech input related functionality") and is a **hard
  error at `--level verified`**.
- `homey:app:com.athom.homeyscript` is explicitly **forbidden** and fails validation outright.
- `homey:manager:api` triggers a warning at publish level: the app "will require a more thorough
  review. It may take longer than usual to review your app."

### Rules

- **Request only what the app actually needs** — superfluous permissions get the submission rejected.
- **Apps do not auto-update when new permissions are added.** Existing installs stay on the old
  version until the user updates manually, so adding a permission in an update is a soft breaking
  change.
- **`homey:manager:api` is heavily reviewed.** It grants complete control over the Homey, so it may
  only be requested when it *is* the app's main functionality. Allowed: DIY home-alarm systems,
  HomeyScript, Device Groups — i.e. apps that belong in the **Tools** category. Rejected: branded
  apps for lightbulbs, thermostats and other physical devices.
- **Homey Cloud forbids `homey:manager:api` and `homey:app:<appId>`** (no Web API, no app-to-app).

### App-to-app

```javascript
// requires "homey:app:com.athom.otherApp" in permissions — Homey Pro only
const otherApp = this.homey.api.getApiApp('com.athom.otherApp');
const installed = await this.homey.apps.getInstalled(otherApp);
const version = await this.homey.apps.getVersion(otherApp);
```

`ManagerApps` (`this.homey.apps`) exposes `getInstalled(apiApp)` → `Promise<boolean>` ("installed,
enabled and running") and `getVersion(apiApp)` → `Promise<string>`. The `ApiApp` client itself
(requests + realtime events) is documented in `references/web-api-and-realtime.md`.

## Persistent storage {#persistent-storage}

| Need | Use | API | Lifetime |
| --- | --- | --- | --- |
| Per-device, user-visible ("Advanced settings") | **Device Settings** | `this.getSettings()` / `this.setSettings()` + `onSettings()`, declared in `driver.settings.compose.json` | With the device |
| Per-device, back-end/internal | **Device Store** | `this.getStoreValue(key)` / `await this.setStoreValue(key, value)` / `this.getStore()` | With the device |
| App-wide JSON-serializable values | **App Settings** | `this.homey.settings` (`ManagerSettings`) | Survive app restarts; deleted on uninstall |
| Binary / non-JSON-serializable files | **App Userdata** | `/userdata/` folder (writable on Homey Pro) | Until removed |
| Secrets baked into the build | **`/env.json`** | `Homey.env.NAME` | Read-only |

### App Settings — `ManagerSettings`

Any JSON-serializable value. Saved across app restarts, deleted only when the app is uninstalled.

```javascript
'use strict';

const Homey = require('homey');

class MyApp extends Homey.App {

  async onInit() {
    const username = this.homey.settings.get('username');
    this.homey.settings.set('lastRun', Date.now());

    this.log('keys:', this.homey.settings.getKeys());

    this.homey.settings.on('set', (key) => {
      if (key === 'username') this.reconnect().catch(this.error);
    });

    this.homey.settings.on('unset', (key) => {
      this.log('setting removed:', key);
    });
  }

}

module.exports = MyApp;
```

| Method / event | Signature | Description |
| --- | --- | --- |
| `get(key)` | `any` | Get a setting. |
| `set(key, value)` | — | Set a setting (JSON-serializable). |
| `unset(key)` | — | Delete a setting. |
| `getKeys()` | `string[]` | All setting keys. |
| `.on('set', key => …)` | — | Fired when a setting has been set. |
| `.on('unset', key => …)` | — | Fired when a setting has been unset. |

### Device Store vs Device Settings

Prefer per-device storage over app settings whenever the data belongs to one device. Use the
**Device Store** for back-end values (tokens, IP addresses, discovery ids, migration flags) and
**Device Settings** for values the user should see and edit. Details, setting types and the
`onSettings({ oldSettings, newSettings, changedKeys })` contract are in
`references/drivers-and-devices.md`.

### App Settings page

An optional `/settings/index.html` lets users edit App Settings. Most apps should not need one —
device settings are usually the right place, and custom HTML is discouraged because the data often
belongs in a Device Store.

> **Custom app settings views are not supported on Homey Cloud.** Ask for whatever the app needs
> during pairing, and use re-pair views to update it later.

The page must include `<script src="/homey.js" data-origin="settings"></script>` and define
`onHomeyReady(Homey)`, ending with `Homey.ready()` (the view stays hidden until then). The full
settings-view API (`Homey.ready/get/set/unset/on/api/alert/confirm/popup/openURL/__`) and the Homey
CSS style library are documented in `references/custom-views-and-settings.md`.

#### Gotcha — settings pages are sandboxed; delivering a file to the user

The settings page runs in a **sandboxed iframe**: `window.open`, `window.print` and browser downloads
are blocked. To hand a user a generated file (a printable report, an export), serve it over the LAN
from the app and open it with `Homey.openURL(url)`.

```javascript
// app.js — serve the report over the LAN (Homey Pro only; Homey Cloud has no LAN access)
'use strict';

const http = require('http');

async serveReport(html) {
  const token = this.generateToken();                        // random one-time token
  const server = http.createServer((req, res) => {
    if (req.url !== `/report?token=${token}`) { res.writeHead(403); return res.end(); }
    res.writeHead(200, { 'Content-Type': 'text/html' });
    res.end(html);
  });
  await new Promise((resolve) => server.listen(0, resolve));  // 0 = any free port
  const { port } = server.address();
  const address = await this.homey.cloud.getLocalAddress();   // e.g. "192.168.1.20:80"
  const host = address.split(':')[0];
  this.homey.setTimeout(() => server.close(), 5 * 60 * 1000); // short TTL, then tear down
  return `http://${host}:${port}/report?token=${token}`;
}
```

```javascript
// settings/index.html — open it externally (works on desktop AND mobile)
const url = await Homey.api('POST', '/report');   // your api.js returns the LAN URL
Homey.openURL(url);
```

Three traps to avoid:

- **Never branch on the return value of `window.open`.** On **desktop** a blocked `window.open`
  returns `null` (easy to detect), but in the **mobile** Homey app it returns a **non-null but
  invisible** window — so `if (win) { win.document.write(html) }` silently swallows the content and
  the feature looks broken *only on mobile*. Use the LAN + `Homey.openURL(url)` path
  **unconditionally**.
- **`homey app run` uses Docker bridge networking**, so a LAN port the app opens is unreachable from
  your phone or PC. The same code works under `homey app install` (production networking). Test
  LAN-served content with `install`, not `run`.
- **Secure anything you serve.** It is plain HTTP on the local network: gate it behind a generated
  one-time token/password, give it a short TTL, and tear the server down afterwards (as above).

### App Userdata (`/userdata/`)

Writable on Homey Pro, for data that is not JSON-serializable (binary files, images).

> **Danger:** `/userdata/` is publicly served at `https://<homey>/app/<your.app.id>/userdata/`.
> Filenames must be **unguessable** — store `a656d380-c887-4d8b-9ee5-f89de7b65d01.jpg`, never
> `image1.jpg`, and keep the mapping in App Settings.

> **Gotcha:** `/` is not the same directory on both platforms (app sandbox on Homey Pro, Linux root
> on Homey Cloud). Always use `require('./…')` or `path.join(__dirname, …)`, never absolute paths.

### Environment variables — `/env.json`

```json
{
  "CLIENT_ID": "12345abcde",
  "CLIENT_SECRET": "182hr2389r824ilikepie1302r0832"
}
```

```javascript
'use strict';

const Homey = require('homey');

const CLIENT_ID = Homey.env.CLIENT_ID;
const CLIENT_SECRET = Homey.env.CLIENT_SECRET;
```

- Keys must be **uppercase**, values must be **strings**.
- Available anywhere as `Homey.env.<KEY>` (and as `this.homey.env.<KEY>`).
- Typically used for OAuth2 client credentials.
- Add `/env.json` to `.gitignore` — it stays on your computer, but it **is** bundled into the
  published app, so it is not a security boundary: make sure these variables alone do not grant
  access to private resources.

## Gotchas {#gotchas}

- **`ENOENT: no such file or directory, open 'app.json'`** on a fresh Compose-only checkout — the
  generated `/app.json` is missing and Compose reads it *before* `.homeycompose/app.json`, so
  `build`/`run`/`validate` all fail instead of bootstrapping it. Commit the generated `app.json`
  (as `homey app create` does) or drop a placeholder `app.json` containing `{}` first. Never
  hand-edit the generated file afterwards.
- **The app `id` is effectively permanent.** Changing it after the first publish creates a new store
  listing and loses installs and reviews.
- **Pre-release versions (`1.0.0-rc.1`) are rejected** by validation and publishing.
- **`brandColor` must be `#RRGGBB` and dark enough** (brightness ≤ 184) — icons render white on it.
- **`$`-keys never reach `/app.json`.** If a value must survive into the manifest, it cannot be
  named `$something`.
- **A driver template that uses `{{driverName}}` breaks any driver without `name.en`.**
- **Compose rewrites `/locales/*.json`** for every language present in `.homeycompose/locales/`.
- **A locale filename only has to be valid ISO-639-1**, so an unsupported language passes validation
  and is silently never used.
- **`"platforms": ["cloud"]` requires a Homey Verified Developer subscription** and an official
  brand integration; otherwise `homey app publish` fails with *"Your account is not eligible to
  publish apps for Homey Cloud."* Default to `["local"]`.
- **Adding a permission does not push the update** — apps do not auto-update on Homey when new
  permissions are added.
- **`homey:app:com.athom.homeyscript` is a forbidden permission**, and `homey:manager:speech-input`
  is rejected at `--level verified`.
- **A missing permission makes the manager throw**, it does not silently no-op. Guard with
  `this.homey.hasPermission()` when the feature is optional.
- **`hasFeature()` requires Homey v12.7.1+**; on older firmware fall back to `platformFeatures` or
  treat the feature as absent.
- **`platformLocalRequiredFeatures` makes the app uninstallable** on Homey Pros without those
  features — only list a feature the app genuinely cannot work without. Its allowed values
  (`nfc`, `ledring`, `speaker`, `matter`, plus `camera-streaming` in the schema) are a *subset* of
  what `hasFeature()` accepts, and combining it with `"cloud"` in `platforms` is a hard validation
  error.
- **Never override the constructor** of `Homey.App` (or `Driver`/`Device`) — use `onInit()`.
- **Module-level variables are shared between app instances on Homey Cloud.** Keep state on `this`.
- **Bare `setTimeout`/`setInterval` leak** across app destroys — always use `this.homey.setTimeout` /
  `this.homey.setInterval` and clear them in `onUninit()`.
- **Unhandled promise rejections crash the app on Homey Cloud** — append `.catch(this.error)`.
- **`/userdata/` is world-readable over HTTP** at `https://<homey>/app/<app.id>/userdata/` — use UUID
  filenames.
- **`env.json` ships with the bundle.** It keeps secrets out of git, not out of the app.
- **`this.homey.__()` returns `null`** when the key is missing (it does not throw and does not echo
  the key), so a typo'd id shows up as `null` in the UI.
- **Editing the Python dependency array by hand breaks the bundle** — always go through
  `homey app dependencies add|remove|install`. Note the key is `pythonPackages` in homey CLI v4.4.0
  and the homey-lib schema, even though the docs call it `pythonDependencies`.
- **Settings pages are sandboxed iframes** — no `window.open`, no `window.print`, no downloads. On
  mobile a blocked `window.open` returns a *non-null invisible* window, so never feature-detect it;
  serve the file over the LAN and use `Homey.openURL()`. LAN ports are unreachable under
  `homey app run` (Docker bridge networking) — test with `homey app install`.
- **Custom app settings views and the App Web API do not exist on Homey Cloud**; neither do
  `homey:manager:api`, app-to-app permissions, LAN discovery and `ManagerCloud#getLocalAddress()`.
